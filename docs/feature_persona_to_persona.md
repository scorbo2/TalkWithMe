# Persona-to-persona chat

This document describes an addition to the TalkWithMe app.
The goal is to add a new general config option `max_persona_replies` (any number between 1 and 4, inclusive, default is 1).
This value controls how many personas reply to each user prompt. 

## Current state

The current chat flow is perfectly standard: the user types or speaks a prompt, and
one of the configured AI personas answers. The method of deciding which persona should answer
is driven by the current value of the "Who should answer?" chooser in the left panel:

- LLM decides: the `router_hints` for each persona in the current chat room are sent to the LLM with the user's prompt, 
  and the LLM returns the the name of the persona who will answer the user.
- Surprise me: a persona is selected at random from the set of personas in the current chat room.
- Selected persona: the user can click a specific persona to select it, and that persona will answer.

The "Who should answer?" decision can be overridden by the `persona_name_mentions` flag, which will automatically
select a specific persona if the user names on in their prompt.

## Desired state

If `max_persona_replies` is set to 1 (this will be the default value), then the chat flow is unchanged from what
is described in "Current state".

If the number is greater than 1, AND if there is more than one persona in the current chat room, then multiple 
personas may reply by responding not only to what the user prompted, but also to what the other personas before 
them replied with. This is guided by a simple set of rules:

- the same persona cannot generate more than one answer to a user prompt. If `max_persona_replies` is greater than the
  number of personas in the current chat room, then `max_persona_replies` is silently reduced to match the count
  of personas actually present. This also means that the "Who should answer?" chooser only applies to the *first* persona
  to respond. All subsequent persona responses should be randomly chosen from the pool of personas that are present
  in the current chat room, which have not yet responded to the current user prompt.
- after persona A responds, persona B must have access not only to the user's original prompt (and conversation history
  before that), but also to persona A's answer. This might influence persona B's reply, and so on with personas C and D.

If there are no personas assigned to the current chat room, then the current "No one is here" message should be
displayed as before, regardless of the `max_persona_replies` setting.

### Example flow

- `max_persona_replies` is 3.
- There are three personas in the current room (call them "Lucy", "Susan", and "Derek")
- User submits "what is the meaning of life?"
- Derek is selected to reply, so Derek replies with "Every man must find his own meaning in life".
- Lucy then replies with "I agree, the true meaning of life is the quest for meaning itself".
- Susan then replies with "But meaning can also be supplied extrinsically, don't you agree?"

## Config/persistence changes

A new config property `max_persona_replies` is added to the `general` section in `settings.yaml`.
It is not an error if this property is not present. The default value is 1.

## UI changes

The existing "Settings" dialog should be renamed to "Servers" to better reflect its purpose.

A new "Settings" dialog should be introduced to represent the "general" config settings:
- `max_persona_replies`, implemented by this new feature
- `persona_name_mentions`, implemented by a previous feature but never exposed in the UI

Bringing up the settings dialog and changing these settings should cause an immediate write of `settings.yaml` with
the new values as soon as the dialog is confirmed by the user. Changes take effect immedately.

There are no changes needed in the left panel, nor in the main chat window. We just need to expose the property
in the new Settings dialog.

## Addendum: problems discovered during implementation

### The chat cycle is broken

The usual conversation turns with an LLM alternate between `user` and `assistant`:

```
user -> assistant -> user -> assistant
```

With this option enabled, things get weird:

```
user -> assistant -> assistant -> assistant
```

This can confuse the LLM and even result in a `400 Bad Request` on the 3rd or subsequent request to the LLM.

The solution to this was to rewrite the conversation history on every request to the LLM such that each previous
persona response is changed from `assistant` to `user`, so that the LLM thinks it's replying to a user prompt
and not to itself.

### Streaming audio was handled globally

Previously, in TTS streaming mode (sentence-by-sentence), each incoming audio chunk was generated by the same
AI persona. But, with this new option, it's entirely possible for persona A's audio response to come in
after persona B's text response has already begun streaming. Because the audio buffer was global, this resulted
in audio chunks being assigned to the wrong persona, or not being assigned at all. A heavy refactor was required
to assure that each incoming audio chunk is mapped back to the correct persona message that generated it.
